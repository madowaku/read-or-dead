# READ OR DEAD v0.3 設計：URL でつなぐ木構造リレー

状態：**実装済み**（13 章はすべておすすめどおりに決定。workers.dev への公開と、実機・X での確認は未実施）
前提：v0.2.2（白い穴・横→縦の 2 回タップ照準、PR #2）の上に作る。

## 1. 目的

SNS で盛り上がることを主役にする。撃った人が自分の一発を「挑戦 URL」として投稿し、それを開いた人が続きに挑戦する。

- 1 つの問題が 1 本の**木**になる。正解して撃つたびに、その下に新しい枝（ノード）ができる。
- 同じ投稿を何人が開いてもよい。全員がそこから自分の枝を伸ばせる（v0.3 と v0.3.1 を分けずに最初から木にする）。
- 失敗した人の枝はそこで止まる。木全体はほかの枝で続く。
- 端末を回して遊ぶ今のローカルモードはそのまま残す（友だち同士で遊ぶ用のサブモード）。

## 2. 最初に作る範囲

| 作る | 後に回す |
| --- | --- |
| 内蔵 300 問から木を作る | 自作問題の公開（禁止語・通報の仕組みが要る） |
| URL を開く → READY? → 回答 → 撃つ → 自分の URL を投稿 | 今日のお題（デイリー） |
| 失敗したら、自分の枝の逆再生と答えを見せる | 撃った人の名前 |
| URL ごとのリンクカード（予告画像・タイトル） | 木の記録ページ・みんなの記録（v0.4） |
| Wordle 風の、ネタばれしない投稿文 | ひっかけ問題・KILL SHOT（別に進める） |
| 問題ごとの成績を記録（何発で全滅したか） | 集計画面 |

## 3. 全体の構成

```
ブラウザ ──► Cloudflare Worker（1 つ）
              ├─ 静的ファイル（Vite のビルド結果。今の SPA）
              ├─ /r/:tree/:node   … 挑戦ページ。index.html に OGP タグを差し込んで返す
              ├─ /card/:tree/:node.png … リンクカード画像
              └─ /api/...         … ゲームの API
                     │
                     ▼
              Durable Object「Tree」（SQLite 版。1 つの木 = 1 つのオブジェクト）
```

- **Worker が 1 つ**で、静的ファイル・リンクカード・API をまとめて返す。GitHub Pages は決まったファイルしか返せず、URL ごとに違うリンクカードを出せないため。
- **1 つの木を 1 つの Durable Object が担当する。** 処理が必ず 1 件ずつ進むので、同じ参加権での二重回答や二重射撃をロックなしで防げる。木ごとの記録は、そのオブジェクトの SQLite に持つ。
- 木をまたぐ集計（v0.4 の「みんなの記録」）が必要になったら D1 を足す。v0.3 では使わない。
- 道具は `cf` CLI（beta）と `cloudflare.config.ts`、Cloudflare Vite プラグインを使う。Wrangler の設定ファイルは作らない。

```ts
// cloudflare.config.ts（案）
import { defineConfig, exports } from "cf/config";
import * as entrypoint from "./worker/index.ts" with { type: "cf-worker" };

export default defineConfig({
  worker: {
    name: "read-or-dead",
    entrypoint,
    compatibilityDate: "2026-10-01",
    assets: { notFoundHandling: "single-page-application", runWorkerFirst: ["/r/*", "/card/*", "/api/*"] },
    exports: { Tree: exports.durableObject({ storage: "sqlite" }) },
  },
});
```

Worker から自分の Durable Object は `ctx.exports.Tree` で呼べる（`env` の binding は要らない）。呼び出しは fetch ではなく RPC メソッドにする。

### ファイルの置き方

```
src/game/      … 今のまま。normalize / power / sweep / render / questions は Worker とブラウザの両方で使う
src/online/    … 新規。API クライアント（RemoteRelay）、URL の読み取り、カード画像・投稿文
src/app.ts     … 「/r/…」で開かれたらオンラインの画面へ分ける
worker/        … 新規。index.ts（ルーティング・OGP 差し込み）、tree.ts（Durable Object）、card.ts（カード画像）
```

`src/game/relay.ts`（LocalRelay）の冒頭には「Phase 2 ではこの役割をサーバーが担う」とある。その方針どおり、Tree は LocalRelay と同じ手順（参加 → 時計開始 → わかった！ → 回答 → 射撃）をサーバー側で行う。

## 4. URL

```
https://<host>/r/<treeId>/<nodeId>
```

- `treeId`：10 文字の base62（約 59 ビット）。Durable Object は `getByName(treeId)` で引く。
- `nodeId`：その木の中で 6 文字の base62。根（まだ誰も撃っていない状態）は `0`。
- URL が表すのは「根からこのノードまでの射撃の並び」。開いた人はその状態の画像に挑戦する。
- URL に答えや問題の中身は入れない。

## 5. データ（Tree の SQLite）

```sql
CREATE TABLE tree (
  id TEXT PRIMARY KEY,
  question_key TEXT NOT NULL,     -- 内蔵問題のキー（kanji-xxxx / silhouette-12 など）
  created_at INTEGER NOT NULL
);

-- 撃たれた結果の状態。根は id='0'、parent_id=NULL、射撃なし
CREATE TABLE node (
  id TEXT PRIMARY KEY,
  parent_id TEXT REFERENCES node(id),
  depth INTEGER NOT NULL,         -- 何発目か（根は 0）
  x REAL, y REAL, radius REAL,    -- 0〜1 の正規化座標と半径（今の Shot と同じ）
  buzz_ms INTEGER,                -- 撃った人の早押しタイム
  created_at INTEGER NOT NULL
);

-- 1 回の挑戦
CREATE TABLE attempt (
  id TEXT PRIMARY KEY,
  node_id TEXT NOT NULL REFERENCES node(id),   -- 挑戦したノード
  device_hash TEXT NOT NULL,
  token_hash TEXT NOT NULL,
  status TEXT NOT NULL,           -- claimed / started / buzzed / correct / shot / wrong / give-up / expired
  started_at INTEGER, buzzed_at INTEGER, buzz_ms INTEGER,
  answer TEXT,
  child_node_id TEXT REFERENCES node(id),      -- 撃ってできたノード
  created_at INTEGER NOT NULL
);
CREATE INDEX attempt_device ON attempt(device_hash);
CREATE INDEX node_parent ON node(parent_id);
```

- ノードまでの射撃の並びは、`parent_id` を根までたどって作る（SQLite の再帰 CTE）。
- 「何発で全滅したか」などの成績は、`attempt` と `node` から集計できる。別の表は作らない。
- 1 本の木のノード数には上限を設ける（例：2,000）。

## 6. 1 回の挑戦の流れと API

| 手順 | API | サーバーがすること | 返すもの |
| --- | --- | --- | --- |
| URL を開く | `GET /api/trees/:t/nodes/:n` | なし | 何発目か・穴の数・この端末が挑戦済みか。**問題の中身は返さない** |
| 挑戦する | `POST /api/trees/:t/nodes/:n/attempts` | 端末ごとの回数制限を確認し、参加権を発行する | `attemptId` と `token`（1 回だけ返す） |
| READY? を押す | `POST /api/trees/:t/attempts/:a/start` | 時計を開始（`started_at`） | 問題の描画に要る情報（問題キー）と射撃の並び |
| わかった！ | `POST …/buzz`（`clientMs`） | 経過時間から弾の半径を決める | `radius` |
| 回答 | `POST …/answer`（`answer`） | 今の `normalize` で判定する | 正解か。不正解なら答えと、根からこのノードまでの射撃（逆再生用） |
| 撃つ | `POST …/shot`（`x`, `y`） | 範囲を確認し、子ノードを作る | 新しい `nodeId` と挑戦 URL |

- **時計はサーバーで計る。** 早押しの時間は「ブラウザが測った時間」を使う。ただし、サーバーで測った経過時間より 3 秒以上短い値は認めない（通信の遅れは許し、時間をごまかすことは防ぐ）。
- **制限時間。** `start` から 90 秒以内に回答がなければ、`expired`（失敗扱い）にする。アラームは使わず、その挑戦を次に読んだときに締め切る（遊ぶうえでの結果は同じ）。
- 弾の半径はサーバーが決める（`radiusFor` をそのまま使う）。ブラウザから送るのは位置だけ。
- `token` は LocalRelay と同じく、ハッシュにして保存する。

## 7. 公平さとズル対策

| 起こりうること | 対策 | 残るもの |
| --- | --- | --- |
| 投稿の画像を見て、時計が動く前に考える | リンクカードに問題の画像を出さない（8 章） | なし |
| 失敗して答えを知った人が、別の枝でもう一度挑戦する | **同じ木には端末ごとに 1 回だけ**挑戦できる（端末 ID を `localStorage` に置き、ハッシュで照合） | 端末やブラウザを変えればできる（アカウントなしでは防げない） |
| 返信に答えを書かれる | 投稿文に「答えはリプに書かないで」と入れる | マナー頼み |
| ブラウザの開発者ツールで答えを見る | 判定はサーバーで行う | 内蔵 300 問の答えは、ローカルモード用にブラウザ側の JS にも入っている。読み解かれると答えが分かる |
| 開いただけで閉じて、何度も見に来る | 問題は `start` のあとにだけ返す。`start` した時点で 1 回と数える | なし |
| 木や挑戦の大量作成 | Worker で IP ごとの回数を制限する（Rate Limiting binding）。**v0.3 では未実装** | 公開前に入れるか判断する |

## 8. リンクカードと投稿

### 挑戦ページの OGP

`/r/:tree/:node` は、ビルドした `index.html` に Worker の `HTMLRewriter` で次のタグを差し込んで返す。

- `og:title`：「READ OR DEAD｜TURN 004 — 読める？」
- `og:description`：「3 発撃たれた。あなたは読める？ 早く読めるほど大きい弾で次の人を撃てる。」
- `og:image`：`/card/:tree/:node.png`（1200×630）
- `twitter:card`：`summary_large_image`

### カード画像（おすすめ：サーバーで作る「弾痕カード」）

問題の画像は使わない。白い紙に、**撃たれた穴の位置だけ**を描く。何発目かの数字と「読める？」も入れる。

- 何が撃たれたかは分からないので、ネタばれにならない。それでも「どこを撃ったのか」が謎として目を引く。
- 射撃の座標だけから描けるので、サーバーで作れる。文字やロゴは、ゲームのフォントで描いたテンプレート（`tools/card-template.html` で作り、パレット番号の並びにして `worker/card-template.ts` に同梱）を使う。穴と数字だけを Worker で描き足し、`CompressionStream` でパレット形式の PNG（約 20KB）にする。外部ライブラリは使わない。
- 一度作った画像はキャッシュする。ノードは作ったあと変わらないので、ずっと同じ画像でよい。

撃った人の端末で作った画像をアップロードする方式もある。ただ、その方式だと、誰でもこのサイトのドメインで好きな画像を配れてしまう。そのため採らない。

### 投稿文（Wordle 風）

```
READ OR DEAD #a3K9 🎯TURN 004 突破
⚡2.1s 💥11.9%
次はあなたの番。読める？（答えはリプに書かないでね）
https://<host>/r/a3K9xxxxxx/Qm81aZ
```

- 画像も動画も添付しない投稿を基本にする。X は、画像や動画を添付した投稿にはリンクカードを出さないため。
- 動画（今の共有動画・逆再生）は、「動画で投稿」として別のボタンに残す。

## 9. 画面の流れ（オンライン）

1. **挑戦ページ**（`/r/…`）：「TURN 004 に挑戦」「〇発撃たれています」と表示する。挑戦済みの端末には「この木にはもう挑戦しました」と出し、自分の枝の結果へ案内する。
2. **READY?** → 問題を見せる → **わかった！** → 回答。今の answer 画面をそのまま使う。
3. 正解 → **撃つ**。今の shoot 画面（横→縦の 2 回タップ）を使う。
4. 撃った後 → **「この一発を投稿」が一番大きいボタン**。投稿文のコピーと X の投稿画面を開くボタンを置く。動画での投稿は 2 番目に置く。
5. 不正解・ギブアップ・時間切れ → 答えと、根から自分までの枝の逆再生。この画面からも、結果（ネタばれなし）を投稿できる。

## 10. 公開先

- まず `read-or-dead.<アカウントのサブドメイン>.workers.dev` で公開する。独自ドメインは後で決める。
- Workers では今の `vite.config.ts` の `base: "./"`（GitHub Pages のサブパス用）を `/` にする。`/r/a/b` のような深い URL から開くと、相対パスでは JS や CSS が見つからないため。
- GitHub Pages：Workers 版が動くまでは残す。その後はトップページから Workers 版へ案内する。
- 料金：無料プランの範囲に収まる見込み。Workers は 1 日 10 万リクエストまで、SQLite 版 Durable Objects も無料プランで使える。

## 11. 検証

- **単体テスト（Vitest）**：Tree の手順（参加 → 開始 → わかった！ → 回答 → 射撃）、端末ごとの制限、時間切れ、時計のごまかし、二重射撃。Tree の中身（`worker/relay.ts`）は Cloudflare に依存しない形にして、Node の SQLite（`node:sqlite`）を差し込んで動かす。Durable Object 自体と API は `npm run dev` で確かめる。
- **ローカル**：`cf dev` で一通り遊ぶ。Android は今までどおり USB のポート転送で確かめる。
- **本番**：workers.dev に出したあと、実際に X に投稿してリンクカードの表示を確かめる。X がカードをどう表示するかは、実際の投稿でしか確かめられない。
